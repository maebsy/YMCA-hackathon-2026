# 발표 자료 구성안 (10장)

발표 자료는 10장 이내로 알려져 있습니다([README](README.md) 결정 필요 ①에서 확인). 아래는 장마다 **한 문장 메시지 → 내용 → 화면 → 근거**입니다. 숫자와 기능은 [fact-check.md](fact-check.md)에서 ✅인 것만 씁니다.

## 원칙

- **장마다 메시지 하나.** 제목을 완결된 문장으로 씁니다. 제목만 넘겨 읽어도 이야기가 이어져야 합니다.
- **구현한 것을 중심에 둡니다.** 기획안(골든타임 72)의 허니토큰·사고 대응 자동화는 10장 "다음 단계"로 보냅니다(결정 필요 ④).
- **진짜 화면을 씁니다.** 시연 장표는 실제 검사 화면 스크린샷. 예제 데이터 화면은 쓰지 않습니다.
- **숫자에는 출처와 건수를 붙입니다.** 장표 아래에 작게 적습니다.
- 글자는 한 장에 3줄 안쪽. 설명은 대본([script.md](script.md))에 넣습니다.

---

## 1. 표지

- **메시지**: 72hours: AI로 만든 사이트의 보안 문제를, 쉬운 말로 알려 주고 AI 코딩툴로 고치게 합니다.
- 내용: 서비스 이름, 한 줄 설명, 팀 YMCA, 코디세이 AI 해커톤 2026
- 화면: 대시보드 첫 화면 스크린샷을 흐리게 배경으로

## 2. 문제

- **메시지**: 누구나 AI로 사이트를 만들지만, 보안은 만드는 속도를 따라가지 못합니다.
- 내용: 바이브코딩 확산 수치 1개 + 바이브코딩 앱 보안 사고 수치 1~2개
- 근거 후보: 기획안 3·4장(GitHub Octoverse 2025, The Next Web 2026.4, The Register 2026.2). **원문 확인 후에만 사용**
- 화면: 큰 숫자 2개

## 3. 고객과 그 순간

- **메시지**: 사장님은 경고를 받아도 무슨 뜻인지, 무엇을 해야 하는지 모릅니다.
- 내용: 페르소나(예: Lovable·v0와 Supabase로 예약 페이지를 직접 만든 1인 사업자). 기존 도구의 결과물(CVE 번호, 규칙 ID, 코드 diff)과 사장님이 필요한 것("손님 목록이 밖에서 보여요. 이렇게 고치세요")을 나란히
- 근거: 기획안 10장(대상 선정), [competitors.md](../competitors.md)
- 화면: 왼쪽 스캐너 원문, 오른쪽 우리 설명 (같은 탐지 1건)

## 4. 해법 한 장

- **메시지**: 찾고, 쉽게 설명하고, AI 코딩툴로 고치고, 재검사로 끝났는지 확인합니다.
- 내용: 4단계 흐름. ① GitHub 주소 하나로 검사 ② 우선순위와 쉬운 설명 ③ MCP로 AI 코딩툴에 수정 지시 전달 ④ 재검사로 "해결됨" 확인 → 완료 리포트
- 근거: [system-flow.md](../system-flow.md) 1장, [roadmap.md](../roadmap.md) 첫 문단
- 화면: 가로 4칸 흐름도

## 5. 시연 ① 검사와 설명

- **메시지**: 주소만 넣으면 지금 고칠 것부터 사장님 말로 알려 줍니다.
- 내용: 실제 데모 저장소 검사 결과. 우선순위("지금 바로 고치세요", "이번 주 안에 고치세요"), 쉬운 설명, OS별 명령
- 근거: `backend/app/llm/risk.py`(SSVC), `remediation.py`
- 화면: 실제 검사 결과 화면 스크린샷 1장 + 확대한 설명 카드

## 6. 시연 ② 고치고 확인하기

- **메시지**: AI 코딩툴이 수정 지시를 받아 고치고, 재검사가 해결을 확인합니다.
- 내용: AI 코딩툴에서 MCP 도구(`get_fix_prompt`)로 지시를 받아 수정 → 재검사 → "해결됨" → 완료 리포트. **AI가 경고를 숨기는 꼼수**(`nosemgrep` 주석, lockfile 삭제 등)도 잡아낸다는 점을 한 줄로
- 근거: `integrations/mcp-handoff/`, `security_engine/compare.py`, `security_engine/suppression.py`
- 화면: 재검사 전후 비교 스크린샷, 완료 리포트 일부

## 7. 기술 구조

- **메시지**: 탐지는 검증된 스캐너가, 판정은 코드가, 설명은 GPU LLM이 맡습니다.
- 내용: 스캐너 3종 + 우리 규칙 21개 → 정규화·재검사 비교 → SSVC 위험도(코드) → GPU LLM Blue 설명·Red 검증(Qwen3.8-27B 4비트, L4 24GB) → OS별 명령은 템플릿 → 대시보드·MCP. 코드는 외부 AI로 보내지 않음
- 근거: [llm.md](../llm.md), [security_engine/README.md](../../security_engine/README.md), 멘토 권고(탐지와 해석 분리)
- 화면: 블록 다이어그램. "판정 = 코드 / 문장 = LLM / 명령 = 템플릿" 세 칸 강조

## 8. GPU 효과

- **메시지**: GPU LLM 설명을 받은 쪽이 실제로 더 많이 고쳤습니다. (실험 결과에 맞게 고침)
- 내용: A 스캐너 원문 / B GPU 없는 설명 / C GPU LLM / D Red–Blue의 조치 성공률, 이해도
- 근거: [gpu-evaluation.md](gpu-evaluation.md) 5장 결과 표. **실험 전에는 이 장을 비워 둠**
- 화면: 막대그래프 1개 + 건수·평가자 수

## 9. 왜 우리인가

- **메시지**: 개발자용 도구가 놓친 비개발자를, 찾기부터 완료 확인까지 데려갑니다.
- 내용: 경쟁사 4곳(Vibe App Scanner, Aikido, 라온 PTaaS, AI스페라·KISA 무상 점검)과 비교. 우리 쪽: 비개발자 설명, 코드 외부 AI 미전송, 재검사로 완료 확인, 신고서 초안
- 근거: [competitors.md](../competitors.md), [competitors2.md](../competitors2.md). competitors2는 설계 기준이라 **구현된 항목만** 표에 올림
- 화면: 비교 표 (체크 표시)

## 10. 다음 단계와 팀

- **메시지**: 다음은 본인 저장소 연결과 매일 지키기, 그리고 사고 순간의 72시간입니다.
- 내용: 다음 단계 3개(GitHub App으로 본인 저장소만·비공개 저장소, 매일 새 CVE 대조 알림, 허니토큰 기반 사고 탐지와 신고 서포트 강화) + 팀 5명과 맡은 일
- 근거: [roadmap.md](../roadmap.md), 기획안 12~17장
- 화면: 타임라인 3칸 + 팀 사진 또는 이름
